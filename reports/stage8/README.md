# Этап 8 — логи, CI и нагрузка

Проверено 11.10.2026. **Этап выполнен: 180/180 минут веса задач, 100%.**
Это статус выполнения плана; нагрузочный прогон обнаружил пределы текущей реализации,
поэтому он не считается подтверждением безошибочной работы при любой нагрузке.

## Что реализовано

- Профиль Compose `logs`: Elasticsearch, Kibana и Filebeat 9.5.5 с persistent volumes.
- Filebeat читает Docker json-file в Docker Desktop VM, разбирает JSON приложения,
  сохраняет `app.*` и `service.name`; для контейнеров настроена ротация 3 × 10 МБ.
- Явный JSON-шаблон обычного индекса `food-delivery-logs`: одна primary shard, ноль реплик.
  В volume также сохранены первоначальные датированные потоки с 4789 ранними логами;
  новый Filebeat пишет в основной индекс, старые записи не удалялись.
- `make logs-up`, `logs-check`, `logs-stop`, `check-guis`, `load-menu`, `load-orders`, `ci-check`.
- CI workflows во всех четырёх репозиториях; изолированные интеграционные зависимости.
- Необязательный CPU-профиль балансировщика в файл с завершением при SIGTERM.
- Убрана секундная пауза relay после полной пачки из 20 событий. Следующая пачка
  обрабатывается сразу; пустая/неполная пачка и ошибка сохраняют паузу. Проверены
  последовательность, отмена и отсутствие активного опроса пустой очереди.
- Docker-сборки используют ограниченную конкурентность и BuildKit cache;
  документация, скрипты и результаты замеров исключены из образов.

## Условия нагрузки

Apple M1 Pro, 16 GiB RAM, macOS/arm64. Docker Desktop Engine 29.7.2:
10 vCPU, 8 214 851 584 байт RAM (~7.65 GiB). Один PostgreSQL, один Kafka broker,
один Redis, два catalog, один balancer, один orders с relay и один notifications.
Kafka UI, Redis Insight, Prometheus, Grafana, Elasticsearch, Kibana и Filebeat включены.
Список контейнеров и образы сохранены в каждом JSON-отчёте.

Два **отдельных** сценария: 20 клиентов × 180 секунд, keep-alive, один активный
запрос на клиента, пауза 20 мс, без автоматических повторов. Это closed-loop замер
конкретного сценария, не предел пропускной способности. Весь каталог через balancer:
меню по HTTP, создание заказа через orders → balancer → catalog по gRPC.
Limiter включён: пул 10 000 demo users, уникальный Idempotency-Key на попытку.
Во время HTTP-нагрузки не запускались сборки или тесты. CPU-профилирование включено.

| Сценарий | Запросы | RPS всех / успешных | p95 | 429 | 5xx |
|---|---:|---:|---:|---:|---:|
| Меню | 122 400 | 679.91 / 679.91 | 22.03 мс | 0 | 0 |
| Заказы | 44 392 | 246.58 / 246.42 | 186.68 мс | 0 | 30 (503, 0.068%) |

Меню распределилось 61 200 / 61 200. RPC заказов — 22 237 / 22 155:
пул учитывает текущую доступность backend, поэтому нагрузка не обязана делиться
строго поровну во время переходных состояний. Это наблюдение, а не доказательство
конкретной причины каждого изменения доступности.

**Backlog:** максимум 39 418 pending events. После прекращения HTTP-нагрузки
полное опустошение подтверждено через **628.57 с (~10 мин 29 с)**, с точностью
опроса/обновления метрики около 5 секунд. Outbox pending измеряет ещё не опубликованные
события; это не Kafka consumer lag. Доставка в notifications проверена отдельно.
Первоначальный load-script ждал только 120 с и завершился с кодом 1 из-за 503 и
неуспевшей разгрузки. Это сохранено в исходном JSON (`outbox_drained_after_s: null`).
Продолжение измерения находится в `backlog-followup.json`. Для повторения теперь
есть `--drain-timeout` (по умолчанию 900 с); длительность HTTP-нагрузки осталась 180 с.

## Ошибки и сохранность данных

Все 30 HTTP 503 найдены в Elasticsearch; длительность 501.57–2226.37 мс.
Prometheus за тот же интервал сохранил 24 gRPC Canceled и 3 DeadlineExceeded.
Это согласуется с дедлайнами 500 мс для RPC и 2 с для HTTP create на нагруженном
локальном стенде. Существующие HTTP-логи не сохраняют конкретную зависимость,
вернувшую каждую из 30 ошибок; все 503 нельзя достоверно приписать только каталогу.

HTTP подтвердил 44 362 создания, а в БД оказалось **44 363 заказа**: одна операция
сохранилась без успешного ответа клиенту. Сравнение с логами `order creation handled`
выделило ровно этот заказ. Повтор с тем же пользователем, телом и Idempotency-Key
вернул **200 и тот же order_id**. При сетевой ошибке/таймауте нельзя считать,
что записи точно нет: повтор должен сохранять прежний ключ.

Проверены все event_id этого прогона: **44 363 заказа, 44 363 опубликованных события,
44 363 уведомления; отсутствующих и повторных уведомлений — 0**.
Дополнительно проверены 20 уведомлений через HTTP API.
Нагрузочные заказы и уведомления оставлены в учебной БД.

## CPU-профиль

`balancer.cpu.pprof`, разобран через `go tool pprof -top`; вывод — `profile-top.txt`.
Окно профиля 637.53 с, CPU samples 117.55 с. Наибольшие отдельные flat-затраты:
Syscall6 — 21.41%, futex — 9.32%, очистка памяти — 3.40%.
Профиль включает оба прогона и интервалы ожидания. Он описывает только балансировщик;
по нему нельзя измерить CPU/IO PostgreSQL, Kafka или relay. Практический предел,
который показал сценарий записи, — скорость последовательной доставки из outbox.
Профилирование завершено, балансировщик возвращён к обычному запуску.

## Артефакты

- `menu-load.json`, `orders-load.json` — исходные метрики и параметры контейнеров.
- `backlog-followup.json` — отдельное наблюдение до полной разгрузки.

- `grpc-codes.json`, `error-analysis.json` — диагностика 503 и исходные записи.
- `balancer.cpu.pprof`, `profile-top.txt` — профиль и его текстовый разбор.
- `final-health.json`, `checks/` — состояние стенда и протоколы локальных проверок.
