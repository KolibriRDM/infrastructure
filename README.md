# Food Delivery Infrastructure

Отдельный Git-репозиторий для локальной инфраструктуры, совместных команд и сквозных тестов.
Сервисы остаются самостоятельными проектами. Go-модуль здесь нужен только
сквозным тестам; он не импортирует код сервисов.

## Расположение

```text
food-delivery/
  catalog-service/     свой .git, go.mod, миграции и Dockerfile
  orders-service/      свой .git, go.mod, миграции и Dockerfile
  notifications-service/ свой .git, go.mod, HTTP, миграции и Makefile
  infrastructure/      этот репозиторий
```

Compose монтирует миграции из соседних репозиториев. Скрипты собирают каждый
бинарник в его собственном модуле. Общий go.work и локальные replace не нужны.
HTTP-модели сквозных тестов объявлены отдельно от реализаций сервисов.

## Запуск

```sh
cp .env.example .env # только если .env ещё отсутствует
make up
make status
make demo-order
```

`make up` последовательно поднимает PostgreSQL, применяет миграции трёх БД,
добавляет отсутствующее демоменю, запускает Kafka/Kafbat UI и создаёт отсутствующие
топики. Затем собирает и запускает catalog, orders и notifications, ожидая их readiness.
Повторный запуск сохраняет данные и существующие цены меню. Если эти сервисы
уже запущены вручную, останови их перед запуском контейнеров: порты совпадают.

`make apps-up` пересобирает и запускает только приложения на подготовленном стенде.
`make apps-start` запускает уже собранные образы без сборки и скачивания.
`make apps-stop` останавливает приложения, сохраняя БД, Kafka и GUI.
`make logs` показывает логи сервисов, обоих каталогов и балансировщика; Ctrl+C прекращает просмотр.

| Сервис | Протокол и адрес на локальном стенде |
| --- | --- |
| orders | HTTP `127.0.0.1:8080` |
| catalog (backend catalog-1) | HTTP `127.0.0.1:8082`, gRPC `127.0.0.1:9082` |
| catalog-2 | HTTP `127.0.0.1:8085`, gRPC `127.0.0.1:9085` |
| balancer — общий вход каталога | HTTP `127.0.0.1:8084`, gRPC `127.0.0.1:9084` |
| notifications | HTTP `127.0.0.1:8081` |
| PostgreSQL | `127.0.0.1:15432` |
| Kafka с компьютера | `127.0.0.1:19092` |
| Kafka внутри Compose | `kafka:9092` |
| Kafbat UI | HTTP `127.0.0.1:8083`, профиль `ui` |

Orders обращается к catalog по gRPC. В `.env` каталога `CATALOG_GRPC_ADDR=:9082`
задаёт адрес прослушивания, в `.env` orders `CATALOG_GRPC_ADDR=127.0.0.1:9082`
задаёт адрес подключения. Конфигурация, соединения с БД и жизненный цикл каждого
процесса независимы. HTTP `/readyz` каждого сервиса проверяет только свою БД.

В Compose orders обращается к `balancer:9084`, балансировщик выбирает
`catalog:9082` или `catalog-2:9082` на каждый RPC;
приложения используют `postgres:5432` и `kafka:9092` внутри сети Compose.
Отдельные Go-модули, репозитории и образы сохранены. Orders публикует outbox-события,
notifications читает их и сохраняет уведомления с дедупликацией.

В каждом образе есть маленькая Go-команда `/healthcheck`: она проверяет `/readyz`
без shell/curl в distroless. Readiness бизнес-сервисов зависит от собственной БД, поэтому остановка
Kafka не делает HTTP нездоровым. `stop_grace_period` даёт 15 секунд на остановку.
Приложения при запуске зависят от готовности PostgreSQL; подготовкой миграций,
топиков и меню управляет `make up`. Обычный `docker compose up` на пустом стенде
не заменяет этот порядок подготовки.

## Kafka и Kafbat UI

```sh
docker compose --env-file .env -f deploy/compose/compose.yaml --profile ui config --quiet
docker compose --env-file .env -f deploy/compose/compose.yaml --profile ui up -d --wait kafka kafka-ui
docker compose --env-file .env -f deploy/compose/compose.yaml --profile ui ps
docker compose --env-file .env -f deploy/compose/compose.yaml --profile ui logs --tail=100 kafka kafka-ui
```

UI доступен на http://localhost:8083 и подключается к `kafka:9092`.
Go-приложения, запущенные на компьютере, будут подключаться к `127.0.0.1:19092`.
Kafka сообщает клиентам соответствующий advertised listener. Контроллер KRaft
работает на `kafka:9093`; его порт не публикуется на компьютере.

Используются `apache/kafka:4.1.2` и `ghcr.io/kafbat/kafka-ui:v1.4.2`.
Один узел совмещает broker/controller; replication factor служебных топиков — 1.
Kafka хранит данные в volume `food-delivery_kafka_data`; постоянный `CLUSTER_ID`
нельзя произвольно менять при повторном использовании этого volume.
Healthcheck обращается к Kafka API; UI запускается после готовности брокера.

Автосоздание топиков отключено. `make kafka-topics` запускает Kafka/UI и создаёт
отсутствующие топики; `make kafka-describe` показывает их параметры.

| Топик | Партиции | Реплики | Хранение |
| --- | ---: | ---: | --- |
| `food.order-created.v1` | 3 | 1 | 7 дней |
| `food.order-created.dlq.v1` | 3 | 1 | 14 дней |

Повторный запуск создания сохраняет существующие топики и их данные, но не
исправляет отличающиеся настройки. После создания заказа relay публикует событие,
а consumer группы notifications-v1 сохраняет уведомление. Один брокер позволяет
проверить рестарты, но не защищает от потери его диска.

## Существующие данные

Имя Compose-проекта остаётся `food-delivery`; volume — `food-delivery_postgres_data`.
Порт PostgreSQL сохраняется: `127.0.0.1:15432`. Разделение исходников не переносит
и не очищает БД. Роли catalog_app, orders_app и notifications_app разделены;
база уведомлений подготовлена заранее, у нового сервиса есть конфигурация,
модель, миграция, HTTP и работающий Kafka consumer.

Init-скрипт создаёт роли и базы только на пустом volume. Его изменение не обновит
пароли существующих ролей. Обычный `docker compose ... down` сохраняет volume;
`down -v` удаляет данные и для обычной остановки не нужен.

```sh
docker compose --env-file .env -f deploy/compose/compose.yaml ps
docker compose --env-file .env -f deploy/compose/compose.yaml logs postgres
make catalog-version
make orders-version
make notifications-version
```

## Миграция уведомлений

Миграции принадлежат `notifications-service/migrations`, инфраструктура монтирует
их в отдельную команду `migrate-notifications` с ролью `notifications_app`.

```sh
make db-up
make migrate-notifications
make notifications-version
```

Первая миграция создаёт `notifications`: UUID уведомления, события, заказа и
пользователя, вид, статус и время создания. UNIQUE(event_id) обеспечивает
дедупликацию; индекс (user_id, order_id, created_at) обслуживает чтение.
Внешних ключей в другие сервисы нет. Допустимы kind=order_created и status=simulated.
После успешного применения версия — `1`, без отметки dirty. Повторный `up`
возвращает `no change`. Общая цель `make migrate` включает все три сервиса.
`NOTIFICATIONS_MIGRATION_DB` позволяет выбрать отдельную тестовую базу;
по умолчанию используется `notifications_db`.

## Проверки

```sh
make test-catalog-postgres
make test-orders-postgres
make test-notifications-postgres
make test-business # menu PATCH, statuses and order snapshots
make test-day2     # тот же набор, прежнее название команды
```

Скрипты создают отдельные БД с уникальными именами, применяют миграции и удаляют
их через EXIT trap. Рабочие таблицы не изменяются. При SIGKILL или отказе Docker
удаление временных БД не гарантируется. Используется race detector.

Сквозной тест обращается к orders по HTTP; orders вызывает catalog по gRPC,
а оба процесса работают со своими временными БД PostgreSQL. Проверяются
идемпотентность (включая 10 конкурентных повторов), права чтения и изменения, снимки цен,
outbox, rollback и рестарт orders при остановленном catalog. Тест назначает
каталогу свободный gRPC-порт и передаёт тот же адрес orders. Фикстуры не подменяют
источник данных приложения.

`make test-business` также проверяет PATCH цены и доступности через HTTP:
новый заказ получает новую цену, старый сохраняет снимок, отключённое блюдо
отклоняется без записи заказа и outbox. Проверяются цепочка доставки, отмена
владельцем, запрет чужой отмены, demo staff и два конкурентных HTTP-обновления
с одной expected_version: одно успешно, второе получает 409.

Название `make test-day2` сохранено как прежняя команда того же набора.
Между orders и catalog используется gRPC. Проверка собирает актуальный код
временных процессов и не обновляет образы приложений в Compose.

Тест уведомлений создаёт отдельную `notifications_test_*` базу и применяет
миграцию ролью notifications_app. Проверяются SaveOnce, повтор события,
конкурентные дубли, чтение всех полей, фильтрация по пользователю и заказу,
стабильная сортировка, ограничения БД и отмена при ожидании соединения.
Также проверяются запуск процесса, HTTP, занятый порт и остановка по SIGINT/SIGTERM.
Временная база удаляется при завершении скрипта; рабочая notifications_db
не меняется. Интеграционный тест запускается с `-race`.

## Контракты и отдельные образы

Исходный protobuf-контракт принадлежит catalog-service; orders-service хранит
его точную копию. Каждый сервис выполняет `make generate` в своём модуле;
общего проекта контрактов и прямых Go-импортов между сервисами нет.

Сборка образов из корня этой инфраструктуры:

```sh
docker build -t food-delivery/catalog:local ../catalog-service
docker build -t food-delivery/orders:local ../orders-service
docker build -t food-delivery/notifications:local ../notifications-service
```

Каждая сборка использует только каталог своего сервиса. Сгенерированные `.pb.go`
входят в исходники, поэтому генераторы в Docker-образах не устанавливаются.
Сборка образов не запускает контейнеры приложений.

Третий день посвящён разделению проектов и связи orders → catalog по gRPC.
Публикация pending outbox-событий в Kafka и их обработка отдельным
notifications-service реализованы и проверяются сквозным тестом.

`.env` содержит настройки локального стенда; сервисы используют собственные `.env`
только со своими настройками. После изменения паролей обновляй соответствующие
локальные файлы согласованно. Реальные секреты в Git не входят.

## Проверка outbox relay

`make test-orders-relay` создаёт отдельную временную БД orders и Kafka-контейнер
на свободном порту. Тест запускает настоящий orders, проверяет доставку outbox,
останавливает только тестовый брокер, проверяет pending/retry и доступность HTTP,
затем восстанавливает брокер и проверяет доставку тем же процессом orders.
Также проверяются SIGTERM, запуск без Kafka, SIGINT и ошибка занятого HTTP-порта.
Тестовые процессы, контейнер и БД удаляются после выполнения; рабочая Kafka
не останавливается. Нужны Docker, Go и Python 3 для выбора свободного порта.

## Сквозная проверка событий

`make test-events-e2e` собирает три сервиса с `-race`, создаёт три временные БД,
применяет миграции и загружает тестовое меню. В запущенной Kafka создаются
отдельный топик с тремя партициями и уникальная consumer group.

Проверяется создание заказа через HTTP с обращением к catalog по gRPC,
публикация outbox, сохранение уведомления в PostgreSQL и его чтение через HTTP.
Повторный HTTP-запрос сохраняет тот же заказ. Повторное Kafka-событие подтверждается
без второго уведомления; тест читает committed offset у брокера. Чужому пользователю
уведомление не возвращается. После остановки notifications создаётся второй заказ;
новый процесс той же группы получает накопившееся событие.

Тест удаляет свои процессы, бинарники, БД, топик и consumer group. Рабочие таблицы,
топики и offsets не изменяются, рабочая Kafka не останавливается. Нужны Docker и Go.
Образы PostgreSQL/Kafka запускаются через существующий Compose без пересоздания.
При принудительном убийстве теста очистка временных ресурсов не гарантируется.

## Проверки конкурентного consumer и DLQ

Из каталога `infrastructure`:

```sh
make test-notifications-kafka
make test-events-e2e
```

Первая команда использует настоящую Kafka и отдельные временные топики/группы.
Проверяются retry при имитируемой ошибке БД, повтор после ошибки commit,
отсутствующий DLQ-топик и доставка после его создания, а также rebalance
1 → 2 → 1 участников. Для трёх партиций проверяются порядок 60 событий,
непересекающиеся назначения и сохранённые offsets. Вторая команда проверяет
реальные процессы трёх сервисов, запись уведомлений в PostgreSQL, дубль и рестарт.
Временные ресурсы удаляются; основные топики, группа и базы сохраняются.

Этап 5 принят: оба набора прошли с `-race`. Unit-тесты проверяют лимит обработчиков,
отмену заполненной очереди, deadline пачки и запрет commit до DLQ ack.
Новая переменная notifications `ORDER_CREATED_DLQ_TOPIC` задана в Compose как
`food.order-created.dlq.v1`. Проверки используют актуальный исходный код;
после изменения кода запущенные контейнеры обновляются через `make apps-up`.

## Redis и Redis Insight

```sh
make redis-up
make test-redis
make redis-cli
```

Redis доступен локальным Go-процессам по `127.0.0.1:16379`, контейнерам —
по `redis:6379`. Redis Insight: <http://localhost:5540>, подключение
`food-delivery` создаётся из переменных окружения после первого принятия EULA.
При первом входе пользователь читает условия и подтверждает их в окне
**EULA and Privacy settings**; Usage Data включать не требуется.
До этого список подключений пуст, хотя контейнер и health endpoint работают.
В GUI указывается внутренний
адрес `redis:6379`, а не localhost. Оба опубликованных порта привязаны к loopback;
пароль в этом локальном учебном стенде не используется.

Образы закреплены по digest. Redis использует 128 MiB и политику `noeviction`:
при нехватке памяти запись вернёт ошибку, а не вытеснит счётчики лимитера.
RDB/AOF отключены, данные Redis исчезают при его перезапуске; источником меню
остаётся PostgreSQL. Настройки Redis Insight сохраняются в отдельном volume.

`make test-redis` проверяет PING, запись и чтение уникального ключа с TTL,
его удаление и доступность GUI. Рабочие ключи не удаляются. `make up` также
поднимает Redis и Redis Insight. Catalog использует cache-aside публичного меню:
`menu:v1:<restaurant_id>`, TTL от 60 до 70 секунд, локальный singleflight,
до 16 активных заполнений с собственным таймаутом 2 секунды. Ошибка Redis
переключает чтение на PostgreSQL; PATCH удаляет ключ best-effort. ResolveItems
обходит Redis. `make seed-catalog` после успешного SQL также удаляет ключи двух
деморесторанов best-effort; недоступность Redis не отменяет seed. Параллельное заполнение может вернуть старый снимок в кэш;
допускается устаревание до TTL плюс время заполнения.

После `make up` выполни `make check-menu-cache`. Проверка временно меняет цену
демонстрационной Маргариты на одну копейку, проверяет ключ и TTL, инвалидацию
после PATCH, затем останавливает Redis и проверяет меню и readiness.
В блоке finally она запускает остановленный Redis и восстанавливает исходную
цену, полученную через ResolveItems. Не запускай параллельно изменения этого блюда.
При принудительном завершении процесса восстановление может не выполниться.
Проверка требует доступного демонстрационного блюда. Она не очищает БД и не
использует FLUSHDB; перезапуск Redis очищает его непостоянный кэш.
Итоговый ключ можно посмотреть в Redis Insight, повторив GET меню после истечения TTL.
Команда предназначена для локального учебного стенда и сама не пересобирает сервисы.

Настройки подключения и health endpoint взяты из официальной документации:
[Redis Insight configuration](https://redis.io/docs/latest/operate/redisinsight/configuration/),
[Docker installation](https://redis.io/docs/latest/operate/redisinsight/install/install-on-docker/).


## Проверка лимитера заказов

Orders считает попытки POST /v1/orders: 30 запросов на UUID за 60 секунд с первой
попытки. Счётчик `rate_limit:orders:create:v1:<user_id>` изменяется атомарным Lua.
Повтор с тем же Idempotency-Key расходует лимит, сохраняя бизнес-идемпотентность.
Превышение возвращает JSON 429 и Retry-After, округлённый вверх до секунд.
Ошибка Redis допускает запрос, отменённый контекст останавливает обработку.

```sh
make redis-up
make apps-up
make test-order-rate-limit
make test-business
make check-menu-cache
make check-order-rate-limit
```

`test-order-rate-limit`, `test-business`, `test-day2` и `test-events-e2e` запускаются
через `scripts/with-test-redis.sh`: отдельный контейнер без постоянного хранилища,
случайный loopback-порт, удаление по ID после завершения команды. Образ совпадает
с закреплённым образом рабочего Redis и должен быть загружен (`make redis-up`).
Сквозные процессы получают адрес через FOOD_TEST_REDIS_ADDR; запуск напрямую
без обёртки отклоняется, чтобы временные БД не использовали кэш рабочего стенда.

`check-order-rate-limit` проверяет работающий Compose после пересборки orders:
создание одного заказа и 29 повторов, 429 на 31-й попытке, TTL и Retry-After,

## Go-балансировщик: реализованный HTTP-компонент

В `internal/balancer` готовы пул экземпляров с независимыми atomic-состояниями HTTP/gRPC и HTTP-прокси. Экземпляр выбирается один раз на запрос; общий transport переиспользует соединения. Подключение ограничено 300 мс, ожидание заголовков — 1 с, контекст обращения — 2 с либо меньшим входящим дедлайном. Нет готовых экземпляров — 503, сетевой сбой — 502, таймаут до начала ответа — 504. Ответы самого каталога сохраняются; ошибка после начала тела прерывает передачу, уже отправленный статус не заменяется.

Балансировщик создаёт X-Request-ID и передаёт каталогу. Каталог сохраняет ID длиной 1–128 символов из ASCII-букв, цифр, дефиса и подчёркивания; для отсутствующего/неверного ID создаёт новый. ID служит корреляции, не аутентификации. Заголовок ответа и JSON-ошибки используют тот же ID.

PATCH не повторяется после неоднозначного результата записи: исходящие Idempotency-Key/X-Idempotency-Key и GetBody удаляются, поскольку каталог не реализует идемпотентность PATCH; повторного выбора backend нет. Тело и прикладные заголовки передаются, hop-by-hop заголовки удаляет ReverseProxy. X-Forwarded-* формируются заново. Безопасные внутренние повторы transport до записи запроса не запрещены.

Проверка компонента: `GOWORK=off go test -race -timeout 45s ./internal/balancer`. Тесты покрывают распределение, отказ/возврат экземпляра, request ID, тело/путь/query/заголовки, ошибки и дедлайны, отмену, переиспользование соединений и обрыв ответа PATCH без повторной отправки. HTTP-компонент подключён к cmd/balancer; Конфигурация Compose с двумя каталогами проверена на работающем стенде.


### Генерация контракта балансировщика

Копия `api/proto/catalog/v1/catalog.proto` совпадает с контрактом catalog-service. `make generate` использует buf 1.72.0, protoc-gen-go 1.36.12 и protoc-gen-go-grpc 1.6.2 и создаёт оба файла в `internal/transport/grpc/catalogv1`; настройки находятся в `buf.gen.yaml`. При изменении API синхронизировать копии proto сервисов и повторить генерацию в каждом репозитории. Нового Go-модуля для контракта нет.

Реализован типизированный GRPCProxy: один ClientConn на экземпляр, выбор через NextGRPC на каждый ResolveItems, лимит сообщений 64 КиБ и таймаут 500 мс с сохранением более короткого входящего дедлайна. Передаётся только один x-request-id длиной 1–128 байт; другая прикладная metadata отбрасывается. Коды, сообщения и details ошибок каталога сохраняются. Настраиваемые повторы RPC отключены, повторного выбора экземпляра при ошибке нет. Close закрывает все подключения и собирает ошибки; создание канала не помечает экземпляр готовым.

Проверка HTTP/gRPC-компонентов: `GOWORK=off go test -race -timeout 60s ./internal/balancer ./internal/transport/grpc/catalogv1`. Тесты запускают локальные gRPC-серверы и подтверждают распределение RPC одного соединения, 40 конкурентных вызовов, исключение/возврат экземпляра, статусы с details, metadata, отмену, дедлайны, ограничения сообщений и закрытие подключений. Прогресс этапа 7Б — 100% (240/240). Запуск/остановка приложения и контейнерная приёмка выполнены; контейнерная gRPC-приёмка этим тестом не подменяется.


### Фоновые проверки экземпляров

HealthChecker запускает по одной горутине на backend: первая проверка сразу, затем раз в секунду; проверки одного экземпляра не перекрываются. GET /readyz ограничен 300 мс и 4 КиБ, редиректы запрещены, требуется статус 200 и успешное чтение тела. При неготовности каталога выключаются оба протокола. При успешном HTTP дополнительно проверяется существующий gRPC ClientConn: Idle запускает подключение, ожидание Ready ограничено отдельными 300 мс. Ready подтверждает состояние транспорта, а не выполнение бизнес-RPC; между проверкой и запросом доступность может измениться.

Run вызывается один раз для экземпляра HealthChecker и блокируется до отмены контекста. При выходе остановлены все workers/tickers, оба флага каждого backend сброшены, свободные HTTP-соединения закрыты. gRPC-подключениями владеет GRPCProxy: их закрывает приложение после остановки проверок и обслуживания запросов.

Тесты подтверждают HTTP-статусы, редиректы, границы размера тела, обрыв чтения, таймаут заголовков/тела, отмену, готовность и перезапуск gRPC на прежнем порту, зависшее подключение, периодичность, ограниченную конкурентность и прекращение проверок после возврата Run. Команда проверки прежняя: `GOWORK=off go test -race -timeout 60s ./internal/balancer ./internal/transport/grpc/catalogv1`. HealthChecker подключён к cmd/balancer; Compose проверен на работающем стенде.


### Метрики и служебные маршруты

Добавлен отдельный реестр `NewMetrics(pool)` с метриками `food_balancer_selections_total` (protocol/backend), `food_balancer_requests_total` (protocol/backend/code), `food_balancer_request_duration_seconds` (protocol/backend) и `food_balancer_backend_up` (protocol/backend). Постоянная метка service=catalog-balancer. Доступность читается напрямую из atomic-флагов при scrape. Пустой backend означает, что экземпляр не был выбран; HTTP aborted означает прерывание уже начатого ответа. UUID, URL и request ID в метках отсутствуют.

Конструкторы теперь принимают реестр: `NewHTTPProxy(pool, logger, metrics)` и `NewGRPCProxy(pool, metrics)`. При сборке приложения им передаётся один общий экземпляр Metrics для того же Pool. Существующие тесты адаптированы; изоляция реестров, текущие health-gauges, конкурентная запись и ограничения меток проверены с -race. Подготовлены proxyResponseWriter и функции служебных JSON-ответов.

Метрики подключены внутри ServeHTTP и ResolveItems: успешный выбор backend учитывается отдельно, любой завершённый запрос записывается один раз вместе с длительностью. Ранние ошибки имеют пустую метку backend. HTTP отмена до отправки ответа учитывается диагностическим кодом 499, а прерывание начатого ответа — aborted с сохранением panic ReverseProxy. В gRPC сохраняется итоговый status.Code, при panic записывается Internal и panic передаётся дальше.

NewRouter обслуживает GET/HEAD /healthz (200 независимо от каталогов), /readyz (200 при наличии доступного backend для каждого протокола, иначе 503) и /metrics. Остальные методы этих маршрутов получают 405 с Allow: GET, HEAD; остальные пути передаются HTTP-прокси. Pool.Ready читает флаги без изменения round-robin. Служебные запросы не выбирают каталог и не входят в счётчики проксирования.

Проверены все комбинации готовности двух backend, общие зависимости роутера, отсутствие служебного трафика в метриках, HEAD по настоящему HTTP, статусы HTTP/gRPC, ранние ошибки, отмена, panic и прерывание тела, промежуточный HTTP 103 и доступность Flush. Полный набор тестов балансировщика прошёл с -race. Прогресс 240/240 (100%); сборка приложения, graceful shutdown, Compose и мониторинг проверены.


### Запуск и остановка балансировщика

Добавлен `internal/platform/config.LoadBalancer`: BALANCER_HTTP_ADDR=:8084, BALANCER_GRPC_ADDR=:9084, LOG_LEVEL=info. Фиксированные имена catalog-1/catalog-2 получают адреса из BALANCER_CATALOG_1_HTTP_URL/GRPC_ADDR и BALANCER_CATALOG_2_HTTP_URL/GRPC_ADDR. Локальные значения по умолчанию — HTTP 8082/8085 и gRPC 9082/9085 на 127.0.0.1; в Compose явно переданы контейнерные адреса. Пустые настройки, неверные слушающие адреса/порты и уровень логирования отклоняются; адреса backend дополнительно проверяются NewBackend до запуска серверов. Образец окружения обновлён, рабочая .env не менялась.

Подготовлен `balancer.ShutdownServers(ctx, httpServer, grpcServer, cancelRequests)`: оба сервера завершаются параллельно с общим дедлайном. При истечении срока HTTP-контексты отменяются, HTTP принудительно закрывается, незавершённые RPC останавливаются через grpc.Stop. Проверены штатное завершение активных запросов и принудительная отмена с -race.

В `cmd/balancer/main.go` загружается конфигурация, создаётся JSON-логгер и обрабатываются SIGINT/SIGTERM. `serve.go` собирает общий пул и реестр метрик, оба прокси, проверки готовности и серверы. Оба порта занимаются до запуска обработки запросов; ошибка второго освобождает первый. Ошибка Serve любого сервера завершает всё приложение.

При сигнале остановки оба сервера перестают принимать запросы и получают общий срок 5 секунд для завершения активных. Контекст HTTP-запросов независим от сигнального; отменяется при принудительной остановке или после завершения серверов. Проверки готовности работают до окончания обслуживания, затем приложение отменяет их и ждёт Run; после этого закрывает исходящие HTTP/gRPC-соединения. Ошибки остановки и закрытия gRPC собираются через errors.Join.

Проверены занятые порты и освобождение первого при ошибке второго, отмена до старта, неверный backend, диагностика при недоступном каталоге, завершение активных HTTP/RPC при отмене, освобождение портов и закрытие исходящего gRPC-канала. ShutdownServers отдельно покрыт тестом принудительной отмены по дедлайну. Сборка и go vet пакета cmd/balancer успешны. ### Два каталога и балансировщик в Compose

Первый сервис сохраняет имя `catalog`, в метриках балансировщика это backend `catalog-1`; второй сервис — `catalog-2`. Оба используют один образ `food-delivery/catalog:local`, одну catalog_db и Redis. Каждый процесс имеет собственные пул подключений и singleflight. `make apps-up` сначала собирает четыре разных образа (catalog, balancer, orders, notifications), затем запускает пять процессов приложений без повторной сборки; у catalog-2 нет отдельной сборки.

Балансировщик опубликован на 8084/9084 и обращается к внутренним портам 8082/9082 обоих каталогов. Прямые порты каталогов сохранены для диагностики. Orders в Compose получает `CATALOG_GRPC_ADDR=balancer:9084`; для вручную запущенного orders этот адрес нужно отдельно задать как `127.0.0.1:9084`. Рабочие .env сервисов автоматически не меняются.

Контейнерные зависимости требуют старта обоих каталогов, а не одновременной готовности: балансировщик сам определяет пригодные экземпляры и может работать с одним. Его healthcheck проверяет `/readyz`; `stop_grace_period=15s` превышает внутренний срок shutdown 5 секунд. Orders остаётся одним процессом с одним relay. БД, Redis и сам балансировщик остаются общими точками отказа.

Prometheus собирает два targets в job=catalog и отдельный job=balancer. На dashboard добавлены готовность экземпляров по протоколам, частота выбора backend, коды ответов и p95; легенды доступности и горутин различают instance. Для новых rate/p95 нужны несколько scrape-интервалов и запросы. Счётчики выбора учитывают попытки, а не только успешные ответы.

После готовности ожидаются четыре backend_up=1 (два backend × два протокола) и выбор обоих экземпляров для HTTP/gRPC. Два demo-order создают два учебных заказа и проверяют получение уведомлений. Prometheus должен видеть пять targets приложений: orders, notifications, два catalog, balancer. Grafana подхватывает новые панели из файла автоматически (до 30 секунд). Скрипт check-menu-cache по-прежнему проверяет первый catalog напрямую; распределение запросов проверяется отдельно через 8084.

Приёмка 11.10.2026: этап 7Б завершён — 240/240 (100%). На работающих контейнерах подтверждены равномерное распределение HTTP и отдельных RPC одного соединения, исключение остановленного catalog-2 и его возврат без перезапуска балансировщика. Повторяемый тест: `make check-balancer`. Требует работающего стенда с seed-меню, временно останавливает catalog/catalog-2/balancer и восстанавливает их через cleanup даже при ошибке проверки. Во время измерения не посылай дополнительный трафик: тест проверяет точные приращения счётчиков. При ручном запуске Go тест пропускается без FOOD_BALANCER_COMPOSE_DIR, чтобы обычный integration-прогон не останавливал стенд.
